# Docker — Notes

---

## What is Docker?

Docker lets you **package your application and everything it needs to run** (runtime, dependencies, config) into a single unit — so it runs the same way on every machine.

> No more "it works on my machine." If it runs in Docker, it runs everywhere.

---

## Docker Image

**The blueprint. Static. Not running.**

A Docker image is a read-only snapshot of your app's environment. It contains:
- OS base layer (e.g. `node:18-alpine`)
- Dependencies (e.g. `npm install` output)
- Your source code
- Startup instructions

You define it in a `Dockerfile`. Once built, the image never changes.

```dockerfile
FROM node:18-alpine       # Layer 1 — base OS + Node
WORKDIR /app              # Layer 2 — set working directory
COPY package*.json ./     # Layer 3 — copy your code
RUN npm install           # Layer 4 — install packages
COPY . .                  # Layer 5 — copy your code
CMD ["node", "index.js"]  # Layer 6 — start command

# Option A — use npm to call the script
# npm is the command, run and start:prod are arguments
CMD ["npm", "run", "start:prod"]
# Option B — call node directly (slightly preferred in prod, no npm overhead)
CMD ["node", "dist/main"]
```

**Analogy:** Image = class definition in OOP.

---

## Docker Container

**A running instance of an image. Live. Does actual work.**

A container is what you get when you `run` an image — it's the actual live process with memory, CPU, network, and its own filesystem.

- One image → spin up 10 containers simultaneously
- Each container is isolated from the others
- The image stays untouched no matter what happens inside the container

**Analogy:** Container = object instantiated from a class.

| | Image | Container |
|---|---|---|
| State | Static | Running |
| Analogy | Class | Object |
| Multiple? | One image | Many containers from one image |

---

## Dockerfile → Image → Container

```
Dockerfile  →  docker build  →  Image  →  docker run  →  Container
(instructions)    (build step)   (blueprint)  (run step)    (live process)
```

### Key Commands

```bash
# Build an image from Dockerfile in current directory
docker build -t hello-docker .

# List all images
docker image ls

# Run a container from an image
docker run hello-docker

# List running containers
docker ps

# Stop a container
docker stop <container_id>

# Remove a container
docker rm <container_id>
```

---

## Stop vs Remove

```
docker stop   →  process pauses. Container still exists. Can restart.
docker rm     →  container deleted. All data inside it is gone.
```

**Data inside a container is temporary.** If you remove the container, the data is gone — unless you use a Volume.

---

## Docker Volume — Persisting Data

A volume maps a path **inside** the container to a path **on your host machine**, so data survives container removal.

```yaml
volumes:
  - postgres_data:/var/lib/postgresql/data
```

Without this — every `docker rm` wipes your database completely.

## Docker Compose

When your app needs multiple services (backend + database + cache), Compose lets you define and run them together from a single YAML file.

```yaml
# docker-compose.yml
services:
  backend:
    build: .
    depends_on:
      - postgres

  postgres:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

Compose does three things:
- Starts services in the right order (`depends_on`)
- Creates a shared internal network between all services
- Registers each service name as a DNS entry on that network

---

## Networking — Three Types of Connections

### 1. Laptop → Container (Port Mapping)

```yaml
ports:
  - "3000:3000"   # host_port:container_port
```

Your browser hits `localhost:3000` on your laptop → Docker forwards it into the container. This is the **only door** between your machine and Docker's world.

### 2. Container → Container (Docker DNS)

Every container's `localhost` loops back to **itself only** — it cannot see any other container.

```
Backend container → localhost:5432 → looks inside itself → nothing there ❌
Backend container → postgres:5432  → Docker DNS resolves → Postgres container ✅
```

Docker Compose creates one internal virtual network and assigns each service a DNS name matching its name in the YAML. So `postgres` in the YAML becomes a resolvable hostname inside that network.

```
DATABASE_HOST=postgres   ✅
DATABASE_HOST=localhost  ❌  (points at backend container itself)
```

### 3. Laptop → DB (Possible, but avoid in production)

You *can* expose Postgres to your laptop:
```yaml
postgres:
  ports:
    - "5432:5432"
```

Tools like TablePlus or DBeaver can then connect to `localhost:5432`. Fine for local development.

**In production — never expose the DB port.** No port mapping means DB is only reachable from inside Docker's network — only your backend can talk to it.

| Service | Expose Port? | Reason |
|---|---|---|
| Frontend | Yes | Users need it |
| Backend | Yes | Apps / frontend need it |
| Database | No | Only backend should reach it — security |

## Docker Layer Caching

Docker builds images in layers — one layer per instruction in the Dockerfile. Each layer is cached. If nothing changed in that layer, Docker reuses the cache instead of rebuilding it.

**The rule: if a layer changes, every layer after it is rebuilt from scratch.**

### Why `COPY . .` first is slow

```dockerfile
COPY . .         # copies everything
RUN npm install  # installs packages
```

You change one line of source code → `COPY . .` layer invalidates → `npm install` re-runs → downloads all packages again. Every single build.

### Why splitting it is fast

```dockerfile
COPY package*.json ./   # rarely changes
RUN npm install         # cached until package.json changes
COPY . .                # changes constantly — goes last
```

You change source code → only the last `COPY . .` layer rebuilds → `npm install` layer cache is still valid → Docker skips re-downloading packages.

### The mental model

**Copy what changes rarely before what changes often.**

`package.json` changes maybe once a week. Source code changes dozens of times a day. So `package.json` goes first, locking the install layer high up in the cache.

### One important precision

Layers are cached **on the machine running the build** — not stored permanently. A fresh CI server or a cleared Docker cache means a full rebuild regardless. The cache is local and conditional, not permanent storage.

### Interview answer

> "Docker caches each instruction as a layer. If a layer changes, everything after it rebuilds. So you copy what changes rarely — package.json — before what changes often — source code — to keep the npm install layer cached across builds."

## Image vs Volume — What Needs a Rebuild

**The image is your environment. The volume is your code.**

### Code changes — no rebuild needed

During development, your local folder is mounted into the container via a volume:

```yaml
services:
  backend:
    build: .
    volumes:
      - .:/app
    command: npm run start:dev  # watch mode
```

Code changes flow directly into the running container through the volume mount. NestJS watch mode detects the change and restarts. No `docker build` needed.

### Package changes — rebuild required

When you install a new package, `package.json` changes. That package is not inside the current image — the volume mount cannot help here. You need to rebuild so `npm install` runs again with the new package baked in.

```bash
docker compose up --build   # forces a rebuild before starting
```

### The rule

| What changed | Action needed |
|---|---|
| Source code | Nothing — volume + watch mode handles it |
| New package added | `docker compose up --build` |
| Dockerfile itself changed | `docker compose up --build` |
| Deploying to production | Always rebuild |

### Mental model

```
Development → volume mount + watch mode → instant, no rebuild

Package added → docker build → new image with package baked in
```


The Dockerfile is not a live watcher. It's a recipe you run when the environment changes — not when your code changes.
