## 1. What is Docker?

Docker is a platform for consistently building, running, and shipping applications. It lets you **package your application and everything it needs to run** (runtime, dependencies, config) into a single unit — so it runs the same way on every machine.

> "It works on my machine" is no longer an excuse. If it runs in Docker, it runs everywhere.

## 2. Architecture & Under the Hood

### Virtual Machines vs Containers

| | Virtual Machine (VM) | Container |
|---|---|---|
| **What it is** | Abstraction of hardware resources | Isolated environment for an application (an OS process) |
| **Managed by** | Hypervisors (VirtualBox, VMware, Hyper-V) | Docker Engine |
| **Performance** | Resource-intensive, slow to start | Lightweight, starts instantly |
| **OS** | Runs a full guest Operating System | Shares the host's kernel |

### The Kernel & Cross-Platform

- A **kernel** is the core of an OS. It manages applications and hardware resources. 
- Different OS kernels have different APIs. You cannot run a Windows app on Linux natively because it expects a Windows kernel API.
- Docker containers fundamentally rely on **Linux kernel features**. 
- **How it works on Windows**: Windows 10/11 includes a Linux kernel (via WSL2) alongside the Windows kernel, allowing Linux containers to run natively and seamlessly on Windows.

### Client/Server Architecture

Docker operates on a client/server architecture:
- **Docker Client**: The CLI you type commands into (e.g., `docker run`).
- **Docker Daemon (Engine)**: The background server that does the actual heavy lifting (building, running, shipping). The client talks to the daemon via a RESTful API.

### Docker Registries

Registries are where you publish and share images.
- **Docker Hub** is the most popular public registry (e.g., pulling `node:alpine` or `postgres:15`).

## 3. Core Concepts

### Image vs Container

| | Image | Container |
|---|---|---|
| What it is | Blueprint. Static. Not running. | A running instance of an image. Live. |
| Analogy | Class definition in OOP | Object instantiated from a class |
| State | Read-only, stored on disk | Running process with memory, CPU, network |
| Multiple? | One image | Many containers from one image |
| Created by | `docker build` | `docker run` |

### The Flow

```
Dockerfile  →  docker build  →  Image  →  docker run  →  Container
(recipe)        (build step)   (blueprint)  (run step)   (live process)
```

## 4. Dockerfile — Reference

Each instruction creates a new **read-only layer**. Layers are cached.

| Instruction | Purpose | Example |
|---|---|---|
| `FROM` | Base image to start from | `FROM node:18-alpine` |
| `WORKDIR` | Set working directory inside container | `WORKDIR /app` |
| `COPY` | Copy files/directories from host into image | `COPY package*.json ./` |
| `ADD` | Like `COPY` but also handles URLs and auto-extracts `.tar` files | `ADD archive.tar.gz /app` |
| `RUN` | Run a command during build (baked into image) | `RUN npm install` |
| `ENV` | Set environment variable | `ENV NODE_ENV=production` |
| `ARG` | Build-time variable (not available in final image) | `ARG API_URL=http://localhost` |
| `EXPOSE` | Document which port the container listens on | `EXPOSE 3000` |
| `USER` | Switch to a non-root user for security | `USER app` |
| `CMD` | Default command — **can be overridden** by `docker run` args | `CMD ["node", "dist/main"]` |
| `ENTRYPOINT` | Fixed command — **cannot be overridden** by `docker run` args | `ENTRYPOINT ["node", "dist/main"]` |

> **COPY vs ADD**: Prefer `COPY` for simple file copies — it's explicit. Use `ADD` only when you specifically need URL fetching or tar auto-extraction.

### CMD vs ENTRYPOINT

| | `CMD` | `ENTRYPOINT` |
|---|---|---|
| Can be overridden? | ✅ Yes — `docker run myapp node other.js` | ❌ No — always runs |
| Use case | Flexible default command | Fixed executable (e.g., a CLI tool) |
| Common in | Web apps, APIs | Utility containers |

### Minimal Dockerfile Example

```dockerfile
FROM node:18-alpine       # Layer 1 — base OS + Node
WORKDIR /app              # Layer 2 — set working directory
COPY package*.json ./     # Layer 3 — copy package files first (cache trick)
RUN npm install           # Layer 4 — install packages (cached unless package.json changes)
COPY . .                  # Layer 5 — copy source code (changes often, goes last)
CMD ["node", "index.js"]  # Layer 6 — start command
```

### Secure Dockerfile — Node Version Matters

Running as root inside a container is a security risk. Use a restricted user. But the correct pattern depends on your Node version — they behave differently.

#### Pattern A — Node 14 (USER before WORKDIR)

When `USER app` is set **before** `WORKDIR`, Docker creates `/app` owned by the `app` user. So `npm install` (running as `app`) creates `node_modules/` also owned by `app`. At runtime, react-scripts can write to `node_modules/.cache` without issues.

```dockerfile
FROM node:14.16.0-alpine3.13

RUN addgroup app && adduser -S -G app app
USER app          # ← set BEFORE WORKDIR
WORKDIR /app      # ← /app created and owned by app user ✅

COPY package*.json .
RUN npm install   # runs as app, node_modules/ owned by app ✅
COPY . .

ENV API_URL=http://api.myapp.com
EXPOSE 3000
CMD ["npm", "start"]
```

#### Pattern B — Node 20 (WORKDIR before USER)

In newer `react-scripts` (v5+, shipped with Node 20 era projects), the ESLint cache is created **at runtime** instead of at install time. Since `WORKDIR` is created by root, `node_modules/` is root-owned and `app` can't write to it. Fix: pre-create the cache folder and explicitly hand ownership to `app`.

```dockerfile
FROM node:20-alpine

RUN addgroup app && adduser -S -G app app

WORKDIR /app      # ← root creates /app

# Install as root — full permissions, no errors
COPY package*.json .
RUN npm i
COPY . .

# Pre-create the cache folder and give app user ownership of ONLY this
# react-scripts v5 creates this at runtime, not at install time
RUN mkdir -p node_modules/.cache && chown -R app:app node_modules/.cache

# Drop to restricted user only for running the app
USER app
ENV API_URL=http://my.api.com
EXPOSE 3000
CMD ["npm", "start"]
```

#### Why the Difference?

| | Node 14 / react-scripts v4 | Node 20 / react-scripts v5 |
|---|---|---|
| When is `.cache` created? | During `npm install` (owned by app) ✅ | At first `npm start` (tries to write to root-owned dir) ❌ |
| Pattern | `USER app` before `WORKDIR` | `WORKDIR` before `USER app` + explicit `chown` |
| App user owns `/app`? | ✅ Yes (can write anywhere in /app) | ❌ No (only `.cache` folder is writable) |

> **Principle:** Give the app user access to **only what it needs** at runtime. Everything else stays root-owned and locked.

### CMD — Two Options

```dockerfile
# Option A — via npm (slight overhead, passes through npm)
CMD ["npm", "run", "start:prod"]

# Option B — via node directly (preferred in production, no npm overhead)
CMD ["node", "dist/main"]
```

### Multi-Stage Builds

A multi-stage build uses multiple `FROM` statements in one Dockerfile. Each stage can copy artifacts from previous stages — so you build in a fat image and ship only the lean output.

**Why it matters**: Build tools (compilers, dev dependencies, test runners) don't belong in production. Multi-stage builds let you have a heavy builder stage and a slim production stage — one Dockerfile, no duplication.

```dockerfile
# Stage 1 — Builder (has all dev tools and source)
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install                        # installs ALL deps (including devDeps)
COPY . .
RUN npm run build                      # compiles TypeScript → /app/dist

# Stage 2 — Production (lean, no compiler, no devDeps)
FROM node:18-alpine AS production
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev             # only production dependencies
COPY --from=builder /app/dist ./dist   # pull ONLY the compiled output from builder
EXPOSE 3000
USER node
CMD ["node", "dist/main"]
```

| | Builder stage | Production stage |
|---|---|---|
| Contains | Dev deps, source, build tools | Prod deps + compiled output only |
| Final image size | Large | Small ✅ |
| Ships to prod? | ❌ Discarded after build | ✅ Yes |

> **`COPY --from=builder`** is the key instruction — it reaches into a *previous stage* and pulls specific files/folders. The builder stage itself is never included in the final image.

> You can also target a specific stage for local dev: `docker build --target builder -t myapp:dev .`

## 5. Docker Layer Caching

Docker caches each layer. If a layer changes, **every layer after it rebuilds from scratch**.

### The Rule

> Copy what changes **rarely** before what changes **often**.

| Order | Effect |
|---|---|
| `COPY . .` first, then `RUN npm install` | Change one source file → npm install re-runs every time ❌ |
| `COPY package*.json ./` first, then `RUN npm install`, then `COPY . .` | Change source file → only last COPY rebuilds, npm install cached ✅ |

```dockerfile
# ❌ Slow — cache busted on every source change
COPY . .
RUN npm install

# ✅ Fast — install layer cached until package.json changes
COPY package*.json ./
RUN npm install
COPY . .
```

> **Important:** Cache is local to the machine running the build. A fresh CI server = full rebuild regardless.

## 7. Docker Volume — Persisting Data

Data inside a container is **temporary**. When the container is removed, data is gone — unless you use a Volume.

A volume maps a path inside the container to a path on your host (or a named volume managed by Docker), so data survives container removal.

```yaml
volumes:
  - postgres_data:/var/lib/postgresql/data  # named volume
  - .:/app                                   # bind mount — syncs local folder into container
```

### Volume Use Cases

| Type | Syntax | Use case |
|---|---|---|
| Named volume | `postgres_data:/var/lib/postgresql/data` | Database persistence |
| Bind mount | `.:/app` | Dev hot reload — local code syncs into container |

### Volume CLI Commands

| Command | What it does |
|---|---|
| `docker volume ls` | List all volumes |
| `docker volume create app-data` | Create a named volume called `app-data` |
| `docker volume inspect app-data` | Show details about a volume (mount path, driver, etc.) |
| `docker run -v app-data:/app/data <image>` | Mount named volume into container at `/app/data` |
| `docker run -v $(pwd):/app <image>` | Bind mount — Linux/Mac syntax |
| `docker run -v ${PWD}:/app <image>` | Bind mount — **Windows PowerShell** syntax (`$(pwd)` doesn't work on Windows) |

### Copying Files Between Host and Container

| Command | What it does |
|---|---|
| `docker cp <containerID>:/app/log.txt .` | Copy file **from** container to current host directory |
| `docker cp secret.txt <containerID>:/app` | Copy file **from** host **into** container |

## 8. Image vs Volume — When to Rebuild

**The image is your environment. The volume is your live code.**

| What changed | Action needed |
|---|---|
| Source code only | Nothing — bind mount + watch mode handles it |
| New package added | `docker compose up --build` |
| Dockerfile changed | `docker compose up --build` |
| Deploying to production | Always rebuild |

```
Dev workflow:
  code change → synced via volume → watch mode restarts → instant ✅

Package added:
  package.json changed → docker build → new image with package baked in ✅
```

## 9. Docker Compose

When your app needs multiple services (backend + database + cache), Compose lets you define and run them all from a single YAML file.

```yaml
# docker-compose.yml
services:
  backend:
    build: .
    depends_on:
      postgres:
        condition: service_healthy   # wait until postgres is actually ready
    ports:
      - "4000:4000"

  postgres:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

### Real-World Example — Multi-Service App (Vidly)

A full-stack app: React frontend + Express API + MongoDB, plus a dedicated test runner container.

```yaml
# docker-compose.yml
version: "3.8"

services:
  web:
    build: ./frontend
    ports:
      - 3000:3000
    volumes:
      - ./frontend:/app    # bind mount — live code sync for hot reload

  web-tests:
    image: vidly_web        # reuse the already-built frontend image
    volumes:
      - ./frontend:/app
    command: npm test       # override the default CMD to run tests instead

  api:
    build: ./backend
    ports:
      - 3001:3001
    environment:
      DB_URL: mongodb://db/vidly   # 'db' = service name, resolved by Docker DNS
    volumes:
      - ./backend:/app
    command: ./docker-entrypoint.sh  # custom entrypoint for migrations + start

  db:
    image: mongo:4.0-xenial
    ports:
      - 27017:27017
    volumes:
      - vidly:/data/db     # named volume — survives container removal

volumes:
  vidly:
```

| Service | Key concept |
|---|---|
| `web` | Bind mount syncs local code — no rebuild needed for frontend changes |
| `web-tests` | Reuses the `vidly_web` image, just overrides the command to `npm test` |
| `api` | `DB_URL` uses `db` (service name) not `localhost` — containers talk via DNS |
| `db` | Named volume `vidly` persists DB data even if the container is removed |

### What Compose Does

| Feature | What it means |
|---|---|
| `depends_on` | Starts services in the right order |
| `condition: service_healthy` | Waits until healthcheck passes, not just "container started" |
| Internal network | All services can talk to each other by service name |
| `volumes` (top-level) | Declares named volumes that persist across restarts |

### Healthcheck — Why It Matters

`depends_on: postgres` alone just waits for the container to start — **not for Postgres to be ready to accept connections**. The healthcheck with `pg_isready` actually checks if Postgres is ready. Without it, your API might crash on startup because it connected before Postgres was ready.

### Docker Compose CLI Commands

| Command | What it does |
|---|---|
| `docker-compose build` | Build (or rebuild) images defined in `docker-compose.yml` |
| `docker-compose build --no-cache` | Force a full rebuild — ignores all cached layers |
| `docker-compose up` | Build images (if needed) + create + start all services (foreground) |
| `docker-compose up -d` | Same as above but in the background (detached mode) |
| `docker-compose up --build` | Force a rebuild of images before starting containers |
| `docker-compose down` | Stop + remove containers and networks (volumes are preserved) |
| `docker-compose ps` | List containers managed by this Compose file and their status |
| `docker-compose logs` | View output logs from all services |

> **`up` vs `up --build`**: `up` only builds if the image doesn't already exist. `up --build` forces a rebuild every time — use this after changing your Dockerfile or adding a new dependency.

### Dev vs Prod — Compose Override Pattern

Docker Compose supports layering multiple files. You have a **base** file with shared config and **override** files for each environment. Files merged left-to-right — later files win on conflicts.

#### The Three Files

**`docker-compose.yml`** — shared base (no environment-specific details)

```yaml
version: "3.8"

services:
  web:
    build: ./frontend
    ports:
      - 3000:3000

  api:
    build: ./backend
    ports:
      - 3001:3001
    environment:
      DB_URL: mongodb://db/vidly

  db:
    image: mongo:4.0-xenial
    volumes:
      - vidly:/data/db

volumes:
  vidly:
```

**`docker-compose.override.yml`** — development overrides (auto-loaded by default)

```yaml
# Automatically merged with docker-compose.yml when you just run `docker-compose up`
version: "3.8"

services:
  web:
    volumes:
      - ./frontend:/app    # bind mount for hot reload
    environment:
      NODE_ENV: development

  api:
    volumes:
      - ./backend:/app     # bind mount for hot reload
    environment:
      NODE_ENV: development
    command: npm run dev   # watch mode

  web-tests:
    image: vidly_web
    volumes:
      - ./frontend:/app
    command: npm test
```

**`docker-compose.prod.yml`** — production overrides (explicitly passed with `-f`)

```yaml
version: "3.8"

services:
  web:
    environment:
      NODE_ENV: production
    restart: unless-stopped   # auto-restart if container crashes

  api:
    environment:
      NODE_ENV: production
    command: node dist/main   # run compiled output, not dev server
    restart: unless-stopped
```

#### How to Run Each Environment

| Environment | Command |
|---|---|
| Development | `docker-compose up` — base + override.yml auto-merged |
| Production | `docker-compose -f docker-compose.yml -f docker-compose.prod.yml up -d` |
| Prod + rebuild | `docker-compose -f docker-compose.yml -f docker-compose.prod.yml up --build -d` |

> **Why not put everything in one file?** Dev needs bind mounts and watch mode. Prod needs `restart: unless-stopped` and compiled output. Mixing them leads to one bloated file you have to comment/uncomment — the override pattern keeps each environment's concerns clean and separate.

> **`.override.yml` is automatic** — Docker Compose always auto-merges `docker-compose.override.yml` when it exists. You don't pass it with `-f`. This is intentional — it's designed to be the dev-defaults layer.

## 10. Networking

### Three Types of Connections

| Connection | How | Example |
|---|---|---|
| Laptop → Container | Port mapping | `ports: "3000:3000"` |
| Container → Container | Docker DNS (service name) | `DATABASE_HOST=postgres` |
| Laptop → DB (dev only) | Expose DB port | `ports: "5432:5432"` |

### The localhost Trap

```
Backend container → localhost:5432 → looks inside ITSELF → nothing ❌
Backend container → postgres:5432  → Docker DNS → Postgres container ✅
```

Every container's `localhost` points to **itself only**. Use the **service name** to reach other containers.

```
DATABASE_HOST=postgres   ✅  (service name = DNS entry in Docker network)
DATABASE_HOST=localhost  ❌  (points at the backend container itself)
```

### Port Exposure — Production Rule

| Service | Expose port? | Reason |
|---|---|---|
| Frontend | ✅ Yes | Users access it from browser |
| Backend | ✅ Yes | Frontend / clients need it |
| Database | ❌ No | Only backend should reach it — security |

### Network Diagram

```
Your Laptop
│
├── localhost:3001 ──► Frontend Container
├── localhost:4000 ──► Backend Container
└── (no port)          Postgres — internal only

        Docker Internal Network
        ┌──────────────────────────────┐
        │  frontend  →  172.18.0.2    │
        │  backend   →  172.18.0.3    │
        │  postgres  →  172.18.0.4    │
        │  (talk via service name DNS) │
        └──────────────────────────────┘
```

## 11. Linux File System

Everything starts at `/` (called **root**). No drive letters like Windows.

```
/
├── bin      → essential commands (ls, cp, echo...)
├── etc      → config files for installed software
├── home     → user personal files (/home/john, /home/jane)
├── root     → home folder for root (admin) user
├── var      → logs, temp files, changing data
├── tmp      → temporary files (cleared on restart)
├── dev      → devices as files (keyboard, disk...)
├── proc     → running processes as files
└── usr      → user-installed programs and libraries
```

### Windows vs Linux

| | Windows | Linux |
|---|---|---|
| Start point | `C:\` | `/` |
| Philosophy | Files and folders | Everything is a file (devices, processes, sockets) |
| Multiple drives | `C:\`, `D:\` separate trees | All mounted under one `/` tree |
| Path separator | `\` | `/` |

## 14. Space Management — Reclaiming Docker Disk Space

Docker accumulates disk space over time — dangling images, stopped containers, unused volumes, build cache, and a bloated WSL2 virtual disk (`.vhdx`). This section covers the full cleanup sequence, from soft prunes to compact the actual disk file.

> **Run these in order — each step targets a different type of waste.**

### Step 1 — Soft Prune (Safe)

Removes only **stopped containers, dangling images, unused networks, and build cache** — does **not** touch volumes or images that are still tagged.

```bash
docker system prune
```

### Step 2 — Aggressive Prune (Removes All Unused Images)

Same as above but also removes **all unused images** (not just dangling ones). If an image isn't attached to a running or stopped container, it's gone.

```bash
docker system prune -a
```

### Step 3 — Clear Build Cache

The build cache can grow very large. This force-removes all of it.

```bash
docker builder prune -a -f
```

### Step 4 — Prune Everything Including Volumes

This is the nuclear option — removes **all unused images + all unused volumes**. Run this only if you don't need any persisted volume data.

```bash
docker system prune -a --volumes
docker builder prune -a -f
```

### Step 5 — Remove Specific Named Volumes

To remove only unused named volumes (without touching images):

```bash
docker volume prune
```

---

### Step 6 — Compact the WSL2 Virtual Disk (`.vhdx`)

Even after pruning, Docker's **WSL2 disk file** (`docker_data.vhdx`) doesn't shrink automatically — it holds onto the freed space internally. You have to compact it manually using Windows `diskpart`.

#### 6a — Quit Docker completely

Right-click the Docker icon in the system tray → **Quit Docker Desktop**, or kill the process from Task Manager. Docker must not be running.

#### 6b — Shut down WSL

```powershell
wsl --shutdown
```

#### 6c — Check the current VHDX size

```powershell
Get-ChildItem "$env:LOCALAPPDATA\Docker\wsl" -Recurse -Filter *.vhdx |
  Select-Object FullName, @{N="Size (GB)"; E={[math]::round($_.Length/1GB, 2)}}
```

This shows you the actual file sizes on disk before compaction.

#### 6d — Compact the disk with `diskpart`

Open a **PowerShell or Command Prompt as Administrator**, then run:

```
diskpart
```

Inside the `diskpart` prompt, run these commands **one at a time**:

```
select vdisk file="C:\Users\Decider\AppData\Local\Docker\wsl\disk\docker_data.vhdx"
attach vdisk readonly
compact vdisk
detach vdisk
exit
```

| Command | What it does |
|---|---|
| `select vdisk file=...` | Points diskpart at the Docker virtual disk file |
| `attach vdisk readonly` | Mounts the disk read-only (needed before compaction) |
| `compact vdisk` | Physically shrinks the `.vhdx` file to reclaim space |
| `detach vdisk` | Unmounts the disk — safe to restart Docker after this |
| `exit` | Closes diskpart |

> **Why does the VHDX not shrink automatically?** A virtual disk works like a sparse file — when Docker deletes data, it marks those blocks as free internally but the `.vhdx` file on your host stays the same size. `compact vdisk` physically rewrites the file, removing the empty blocks.

### Full Cleanup — Summary

| Step | Command | What it cleans |
|---|---|---|
| 1 | `docker system prune` | Stopped containers, dangling images, unused networks, build cache |
| 2 | `docker system prune -a` | All of the above + all unused images |
| 3 | `docker builder prune -a -f` | All build cache |
| 4 | `docker system prune -a --volumes` | Everything above + unused volumes |
| 5 | `docker volume prune` | Named volumes not attached to any container |
| 6 | `wsl --shutdown` + `diskpart compact` | Physically shrinks the WSL2 VHDX file on host disk |
